# Security и legal: анализ приглашения Baby Boss

Документ **информационный**, не является юридической консультацией (legal advice) и не заменяет оценку юриста / специалиста по privacy.

Проект: статическое приглашение на GitHub Pages + Cloudflare Worker для уведомлений через Telegram Bot API.

---

## 1. Security — безопасность

### 1.1. Secrets handling — работа с секретами

| Что | Где | Оценка |
|-----|-----|--------|
| `TELEGRAM_BOT_TOKEN` | Cloudflare Worker secrets / локальный `.env` | Правильно: **не** в frontend |
| `TELEGRAM_CHAT_ID` | То же | Правильно: **не** в frontend |
| `.env` | Корень репозитория (локально) | Не коммитить; в репозитории есть `.env.example` без значений |
| Frontend / `config.json` | Публичный URL Worker | Секретов нет — только endpoint |

**Вывод:** bot token не зашит в HTML/JS — это корректная модель. Риск утечки — через commit `.env`, логи CI, скриншоты Dashboard или утечку Worker secrets.

**Рекомендации:**
- Никогда не коммитить `.env`.
- При утечке token — сразу revoke / regenerate у [@BotFather](https://t.me/BotFather).
- Worker secrets хранить только в Cloudflare Dashboard (Variables / Secrets).

### 1.2. Telegram bot token exposure

- Frontend вызывает только публичный Worker URL из `config.json`.
- Token подставляется на сервере Worker / в `tools/server.py` из окружения.
- В ответах API после правок локального server сырое тело ошибки Telegram **не** пробрасывается клиенту (раньше могло утекать в JSON error).

Остаточный риск: любой, кто знает Worker URL, может вызывать notify endpoint (см. spam ниже). Это не даёт token, но даёт канал в ваш Telegram chat.

### 1.3. GitHub Pages — статическая публичность

Всё, что лежит в репозитории и публикуется на Pages, **доступно всем по URL**:
- `index.html`, `css/`, `js/`, `config.json`
- `assets/design.jpg`, `assets/birthday-person.gif`, `assets/birthday-person.jpg`
- текст приглашения: имя ребёнка, адрес ресторана, дата/время

Это не «закрытая вечеринка» на уровне сети: ссылка = доступ. «Закрытость» только социальная (кому вы отправили URL).

### 1.4. `config.json`

Публично содержит:
- `notifyUrl` — URL Cloudflare Worker (ожидаемо для production)
- `telegramUsername` — сейчас пустой (fallback deep-link в Telegram неактивен)

Риски placeholder:
- Если оставить тестовый / чужой Worker URL — уведомления уйдут не туда или сломаются.
- Если случайно вписать token в `config.json` — критическая утечка (сейчас этого нет).

### 1.5. XSS (Cross-Site Scripting)

- Имя гостя выводится через `textContent` / классы статуса — **не** через `innerHTML`. Хорошо.
- Worker вставляет имя в текст Telegram-сообщения (не HTML страницы). Добавлена нормализация: control characters, длина ≤ 60.

Остаточный риск XSS низкий при текущем коде. Не добавлять `innerHTML` с данными гостя без санитизации.

### 1.6. CORS `Access-Control-Allow-Origin: *`

И в Worker, и в `tools/server.py` разрешён любой Origin.

- Нужно, чтобы GitHub Pages (`https://kyratop.github.io`) мог делать `fetch` на Worker.
- Минус: любой сайт в браузере может дергать endpoint (плюс прямой `curl` без CORS вообще).

**Рекомендация (defense in depth):** ограничить Origin списком, например `https://kyratop.github.io`, понимая что rate limit важнее CORS против ботов.

### 1.7. Rate limiting и spam abuse notify endpoint

**Ранее:** открытый endpoint без лимитов.

**Сейчас в коде:**
- Soft **rate limit** (~8 запросов / IP / час) в Worker (Cache API) и в `tools/server.py`
- **CORS allowlist** (`https://kyratop.github.io`, localhost)
- Опционально **Cloudflare Turnstile** (`TURNSTILE_SECRET_KEY` + `turnstileSiteKey` в `config.json`)

Пока `TURNSTILE_SECRET_KEY` не задан, Turnstile на Worker не обязателен (удобно для постепенного включения). Для production рекомендуется включить оба ключа.

**Дополнительно в Dashboard:** Cloudflare Rate Limiting / WAF на Worker route.

### 1.8. PII — персональные данные гостей

- Гость вводит **имя** (`guestName`).
- Имя уходит в Telegram организатору; на сайте в `localStorage` хранится только флаг `babyBossInviteReceived=1`, не само имя.
- Имена не пишутся в статику репозитория, но попадают в Telegram history организатора.

См. также legal / privacy ниже.

### 1.9. Dependency / supply chain

- Frontend: Google Fonts (Nunito, Unbounded) — внешний CDN; при недоступности есть `system-ui` fallback.
- Backend notify: стандартная библиотека Python + `fetch` в Worker — без npm runtime для сайта.
- `tools/make_birthday_gif.py` зависит от Pillow (PIL) локально — не часть Pages bundle.

Риск supply chain низкий; следите за обновлениями Pillow при локальной генерации GIF.

### 1.10. `.env.example`

Содержит только имена переменных без значений — корректно как шаблон. Не копировать реальные secrets в example-файлы.

### 1.11. `tools/server.py` — локальные риски

**Сейчас:**
- `HOST` по умолчанию `127.0.0.1` (только localhost)
- `.env` и похожие файлы **не** отдаются как static
- Soft rate limit на `/api/notify`
- CORS allowlist; опциональная проверка Turnstile

Для LAN-доступа можно временно поставить `HOST=0.0.0.0` в окружении — только в доверенной сети.

### 1.12. Frontend security notes (кратко)

- Секретов в JS нет — правильно.
- `localStorage` легко очистить → повторная отправка RSVP возможна (ожидаемо для UX; усиливает spam-сценарий с одного браузера меньше, чем открытый API).
- `og:image` указывает на публичный asset — нормально для preview.

## 2. Legal / privacy — правовые и privacy-соображения (informational)

> Не formal legal advice. Ниже — общие риски для личного fan/event-проекта.

### 2.1. Copyright — Baby Boss / DreamWorks character art

- Тема и файл `assets/design.jpg` используют визуальный стиль / изображение, связанное с франшизой **The Boss Baby** (DreamWorks).
- Персональное приглашение ≠ лицензия на коммерческое использование IP.
- GitHub Pages = публичная публикация произведения / derivative / fan art.

**Риски (высокая уровень неопределённости, зависит от юрисдикции и правообладателя):**
- претензии по copyright / trademark при заметном публичном использовании;
- особенно если проект масштабировать, монетизировать или выдавать за официальный бренд.

**Практично:** указать в README, что это **личное / fan use**, не аффилировано с DreamWorks; по возможности использовать собственный дизайн без чужих персонажей для долгой публичной витрины.

### 2.2. Личное фото ребёнка (`birthday-person.gif` / `.jpg`)

- Фото несовершеннолетнего в открытом интернете (Pages + репозиторий, если публичный).
- Риски: копирование, индексирование поиском, пересылка третьим лицам, нежелательный context.

**Рекомендации:**
- Закрытый (private) репозиторий, если фото чувствительно; или не коммитить оригинал в public repo.
- Раздавать ссылку только гостям; не публиковать в открытых соцсетях без необходимости.
- Согласие родителей / законных представителей на такую публикацию — этическая и часто правовая норма (152‑ФЗ и аналоги — см. ниже на высоком уровне).

### 2.3. Telegram notifications и consent

- Гость нажимает «Я получил приглашение» → имя уходит организатору в Telegram.
- Явного текста consent («согласен на передачу имени в Telegram») на форме нет.
- Для небольшого private invite часто приемлемо по ожиданию гостей, но прозрачность лучше: одна фраза под кнопкой.

### 2.4. Публичный hosting данных события

Публично видны: ФИО/имя ребёнка, дата, время, адрес заведения. Это convenience для гостей и одновременно **location / schedule disclosure**.

Риск невелик для типичного семейного события, но ссылку лучше не делать «вечной витриной» без нужды после праздника.

### 2.5. Россия / privacy (высокий уровень, не консультация)

В РФ обработка персональных данных регулируется в т.ч. **152‑ФЗ**. Имя гостя + факты о ребёнке могут рассматриваться как персональные данные в широком смысле. Для чисто личного семейного оповещения на практике часто действуют исключения / иной режим, но:

- публичная выкладка фото ребёнка и адреса события — зона осторожности;
- при споре или жалобе формальный разбор зависит от фактов;
- этот документ **не** заменяет консультацию.

Общий good practice: минимизация данных, короткий срок хранения сообщений, понятное назначение обработки, ограничение аудитории ссылки.

## 3. Приоритеты рисков (кратко)

1. **Снижен кодом:** spam notify — rate limit + CORS; полностью закрывается включением Turnstile.  
2. **Высокий (legal/privacy):** публичные фото ребёнка + character IP на GitHub Pages (код это не убирает — нужны ваши решения по контенту).  
3. **Снижен кодом:** локальный `server.py` и раздача `.env`.  
4. **Низкий при текущем коде:** XSS на странице; утечка bot token из frontend (отсутствует).

## 4. Что уже сделано хорошо

- Token / chat id только в Worker secrets и `.env`, не в статике.
- Есть `.env.example` без секретов.
- Имя гостя не кладётся в `localStorage`.
- Ограничение длины имени на клиенте (`maxlength="60"`) и на сервере/Worker (после правок).
- Статический сайт без серверных credentials в browser.
